## 1. Broad vs quoted частота в Yandex Wordstat (ключевая находка)

Yandex Wordstat различает режимы соответствия фразы:

- **Broad** (фраза без операторов, как есть) — считает **любой** запрос, где встречаются эти слова, в любом порядке, с любыми дополнительными словами, в любой словоформе. Отражает спрос на **всю семью фраз** вокруг формулировки, а не на неё саму.
- **Quoted** (фраза в кавычках — оборачивается прямо в строку запроса: `"redmi note"`) — только точный порядок слов, без посторонних слов между/вокруг. Отражает спрос **именно на эту формулировку**.

Quoted всегда ≤ broad (строгое подмножество). Расхождение между ними **непредсказуемо и зависит от конкретной фразы** — проверено на реальных данных: от 2× до **1300×** (пример: «redmi note» — broad 3949, quoted 3, регион Севастополь).

**Если используется MCP-инструмент типа `wordstat_bulk`/аналог** — по умолчанию (без кавычек в строке) он с высокой вероятностью возвращает **broad**. Проверить эмпирически: взять любую фразу, прогнать без кавычек и в кавычках (`"фраза"`), сравнить. Если числа совпадают — инструмент не поддерживает режим кавычек, нужно проверять описание API/MCP-сервера отдельно.

**Правило применения:**
- **Относительные сравнения** (кириллица vs латиница, формальный vs разговорный термин, какой вариант написания выбрать для заголовка) — можно использовать **broad**: обе стороны сравнения измерены одинаково, соотношение не искажается даже если абсолютные числа завышены.
- **Пороговые/бинарные решения о спросе** (стоит ли включать факт в текст, стоит ли трекать запрос, demand-filter «есть ли спрос на composite-фразу товар+условие») — использовать **только quoted**. Broad для составных фраз (товар + гарантия/доставка/трейд-ин и т.п.) почти всегда даёт крошечные ненулевые числа, которые ничего не говорят о реальном спросе на точную фразу.
- Если broad = 0 — quoted можно не проверять, гарантированно тоже 0 (экономия запросов).
- Собирать оба числа одним батчем, где это возможно — добавить в список каждую фразу дважды (обычная форма + `"в кавычках"`).

**Поле `frequency`, если оно приходит из внешнего трекера позиций (аналог PixelPlus)** — скорее всего это **quoted**-число трекера, а не «устаревшее» значение. Не путать «расхождение с нашим live-замером» со «staleness» — сначала проверить гипотезу broad/quoted, прежде чем предполагать, что данные трекера просто старые.

## 2. Скилл расширения семантического ядра категории (не отдельной страницы)

**Назначение:** взять корневой запрос/категорию, найти новые релевантные запросы с реальным спросом, которые ещё не отслеживаются в трекере позиций. **Не определяет**, есть ли под запрос посадочная страница — это решает пользователь сам по выгруженному списку.

### Вход
Один обязательный параметр — корневой запрос/категория. Без URL хаб-страницы (не нужен, т.к. скилл не проверяет покрытие страницей).

### Workflow

1. **Wordstat-кластер (широкий)** — top-запросы + associations/LSI от seed (60-80 фраз). Добавить вручную: кириллица↔латиница варианты бренда/модели, коммерческие модификаторы («купить»/«цена»), гео-варианты, модельный ряд линейки (из самих ассоциаций Wordstat, не только с сайта — иначе гарантированно не найдёте то, чего ещё нет на сайте).

2. **Фильтр релевантности (до проверки частоты)** — исключить только то, что топически не о покупке этой категории, независимо от каталога: сервис/ремонт, аксессуары, софт/контент не про устройство, конкурентные бренды/сторонние домены, явные артефакты токенизации Wordstat. **Не исключать**: старые/новые модели вне видимого ассортимента, б/у, атрибуты (цвет/память), гео — это не задача скилла отсеивать, пусть проходят на проверку частоты, а решение по каждому — за пользователем. Отдельно пометить (не исключать, но не для трекинга): сравнения моделей, «как выбрать» — информационный интент, полезен для FAQ, не для позиционного трекинга.

3. **Частота (broad + quoted)** — оба числа, см. раздел 1. Исключить только broad=0.

4. **Сверка с трекером позиций (обязательна)** — выгрузить **весь проект целиком**, не одну группу/раздел (запрос мог быть добавлен раньше под другим ярлыком). Дедуплицировать. Сравнение регистронезависимое, по нормализованному тексту (`.strip().lower()`), не по точному совпадению строки. Совпадение → не включать в новый список.

5. **Файл-результат** (не отправка в трекер напрямую!) — один файл на категорию (перезаписывается при повторном запуске, не версионируется по дате). Пользователь сам решает по списку: под какие запросы есть страница (трекать/дорабатывать контент), под какие нет (создавать), затем удаляет файл. Формат: пояснения (самодостаточный текст, без отсылок к переписке) + таблица новых запросов (broad + quoted) + информационные отдельно + исключённое кратко для прозрачности + уже трекается для справки.

### Ключевые уроки (набиты на практике, не изобретать заново)
- Не брать список «моделей для проверки» только с текущей страницы категории — тогда проверка «есть ли пробел» становится замкнутым кругом (кандидаты по построению уже имеют страницу).
- Не угадывать URL фильтров/атрибутов (цвет, объём и т.п.) вручную — узнавать через фактический разбор страницы (facet-навигация), slug'и часто неочевидны.
- Автономность: если входной параметр дан — выполнять весь workflow без уточняющих вопросов.

## 3. Что поправить в существующем скилле генерации мета-тегов (если там есть Wordstat-кластерный анализ)

Если в проекте уже есть скилл, аналогичный "meta-builder" (генерация H1/title/description с проверкой частоты через Wordstat) — проверить два места:

1. **Ранжирование кластера для H1/title** — оставить на broad (относительное сравнение, см. раздел 1).
2. **Demand-filter для составных USP-фраз** («[товар] + гарантия/доставка/трейд-ин/кредит» и т.п., решение — включать ли USP в описание) — переключить на **quoted**. Это самое уязвимое место: broad почти всегда даёт ложноположительный «спрос» на такие составные фразы.

## Как использовать при переносе в другой проект

1. Подставить свои значения: project_id трекера, регионы, бренд/специфику категорий.
2. Проверить, какие MCP-инструменты доступны в новом проекте (Wordstat-эквивалент, трекер позиций) — интерфейсы могут отличаться от `wordstat_top`/`wordstat_bulk`/`pixelplus_get_queries`, но принципы (broad/quoted, сверка по всему проекту, файл вместо прямой записи) переносятся один в один.
3. Эмпирически перепроверить гипотезу broad/quoted на новом инструменте перед тем как полагаться на неё — не предполагать, что чужой Wordstat-клиент ведёт себя идентично.
