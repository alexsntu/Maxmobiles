## Mobile Optimization — 9/10 (новое в этом прогоне)

Важный нюанс инфраструктуры: сайт переключает десктоп/мобильный шаблон **по User-Agent на сервере** (`Set-Cookie: ab__device=mobile|desktop`), а не только адаптивной CSS-вёрсткой под ширину окна — поэтому обычный ресайз окна браузера не показывает мобильную версию (нужен реальный мобильный UA). Для проверки мобильный HTML был получен напрямую (`curl` с UA Pixel 8/Chrome) и отрендерен в браузере через локальный HTTP-сервер (в HTML есть `<base href="https://maxmobiles.ru/">`, поэтому все относительные ресурсы подтянулись с настоящего домена).

| Проверка | Результат | Баллы |
|---|---|---|
| Viewport meta tag | Есть, корректный (`width=device-width, initial-scale=1.0`) | 3/3 |
| Responsive-раскладка (нет горизонтального скролла) | Подтверждено: `scrollWidth` (649px) < viewport (657px) | 3/3 |
| Размер тап-таргетов (≥44×44px) | **48% кликабельных элементов (78 из 163) меньше 44px** по одной из сторон | 1/2 |
| Размер шрифта | Базовый `font-size: 16px` — соответствует минимуму | 2/2 |

**Про тап-таргеты подробнее:** в основном это не критично мелкие — иконки 36×36px (на 8px меньше нормы), поле поиска высотой 40px, фильтр-чипы («Акции», «Зарядные станции») высотой 33px. Ни один элемент не экстремально мал, но почти половина интерактивных элементов чуть не дотягивает до рекомендованных Google 48×48px (WCAG — 44×44px). Стоит увеличить padding у иконок и чипов на пару пикселей.

**Отдельно, не в баллах:** `user-scalable=no, maximum-scale=1.0` в viewport — запрещает pinch-to-zoom. Это не проваливает мобильный тест Google напрямую, но является анти-паттерном доступности (WCAG 1.4.4) — пользователи с нарушением зрения не могут увеличить страницу жестом.

## Page Speed & Server — 12/15 (новое в этом прогоне)

Измерено через `curl` (TTFB, заголовки) и Performance API реального Chrome (вес страницы, разбивка по типам ресурсов):

| Проверка | Результат | Баллы |
|---|---|---|
| TTFB < 800ms | Сервер (curl, без сети браузера): **178ms**. Полный TTFB из браузера (`Navigation Timing`, с реальным сетевым RTT и TLS): **761-847ms** — на грани порога | 3/3 |
| Вес страницы < 2MB (критичные < 1MB) | Главная страница: **~2.06 MB** суммарной передачи по сети (gzip уже применён) — на границе общего порога и выше «критичного» порога 1MB | 1/2 |
| Оптимизация изображений | WebP-формат подтверждён у всех проверенных картинок; `loading="lazy"` — только у 33 из 84 `<img>` (~39%); средний вес изображения ~22KB — разумно | 2/3 |
| JS-бандлы (<200KB — warning, <500KB — critical) | 13 файлов, 386KB суммарно; **самый крупный бандл — 253KB** (`scripts-*.js`), превышает warning-порог 200KB, но далеко от критичных 500KB | 1/2 |
| Сжатие (gzip/brotli) | Подтверждено: `Content-Encoding: gzip` на HTML и JS | 2/2 |
| Кеш-заголовки на статике | Отлично: `Cache-Control: max-age=31536000` (1 год) на JS и изображениях | 2/2 |
| CDN | Ngenix подтверждён (`X-NGENIX-Cache`) | 1/1 |

**Отдельная находка (не в баллах Page Speed, но важно):** заголовок `Vary` на HTML-ответе содержит только `Accept-Encoding`, **не `User-Agent`** — при этом контент реально отличается по User-Agent (мобильная/десктопная версия, размер HTML 260KB vs 419KB). Если перед сайтом или у клиента есть кеширующий прокси, который не учитывает `Vary`, он может закешировать и отдать не ту версию не тому устройству. Стоит добавить `User-Agent` в `Vary` (или, лучше, мигрировать на полностью адаптивную CSS-вёрстку без серверного UA-sniffing).

## Core Web Vitals — не измерено официально

`Largest Contentful Paint` API вернул пустой результат в автоматизированном Chrome (`largest-contentful-paint` entries не зафиксировались ни при первой, ни при повторной попытке без взаимодействия) — вероятно, ограничение автоматизированного контекста браузера. `Cumulative Layout Shift` дал 0 в одном замере, но это ненадёжно без полного скролла до конца страницы. Настоящие Core Web Vitals нужно снимать через Lighthouse/PageSpeed Insights (полевые данные CrUX) — эти инструменты недоступны из командной строки в этой среде.

Что удалось снять как косвенный (не сертифицированный) сигнал:
- **First Contentful Paint:** ~1.26-1.51s — если использовать общий FCP-порог "хорошо < 1.8s" (это не входит в 3 официальных CWV, но коррелирует с LCP), это неплохой результат.
- **DOMContentLoaded:** ~2.39s, **полная загрузка (`load`):** ~3.82s — заметно медленнее, что согласуется с находкой про вес страницы (~2MB) и крупный JS-бандл (253KB).

**Рекомендация:** прогнать `https://pagespeed.web.dev/` вручную на `https://maxmobiles.ru/` и на карточке товара — это даст официальные LCP/INP/CLS с полевыми данными, которые эта среда получить не может.

## Итоговые рекомендации (новые, из этого прогона)

### Сделать
1. Увеличить тап-таргеты у иконок/чипов минимум до 44×44px (сейчас 48% элементов меньше).
2. Разбить/лениво загрузить самый тяжёлый JS-бандл (253KB) — он один превышает рекомендованный порог.
3. Добавить `User-Agent` в заголовок `Vary`, раз контент реально зависит от UA.

### Проверить вручную
4. Снять официальные LCP/INP/CLS через PageSpeed Insights — не решается через curl/автоматизацию.
5. Убрать `user-scalable=no` из viewport (доступность).

### Уже хорошо, не трогать
- Сжатие (gzip), кеш-заголовки на статике (1 год), CDN, формат изображений (WebP), TTFB на уровне сервера.
